# 猕猴桃微辣瘦牛肉干：R2 研发案例

日期：2026-10-05。案例 `KJ-001`。当前状态：**已有可重复执行的证据检索与筛选设计，未采购、未制作、未试吃。** R2 改进的是需求表达、路线比较、实验设计和经验记录，没有把 R1 的候选变成经过验证的配方。

用户已确认瘦牛肉，要求猕猴桃风味、没有那么甜、一点辣、不苦、不腻。这些要求保存在 [brief.json](brief.json)。甜味参照、酸度接受度、肉干软硬偏好、实际原料批次与保存目标仍未确定，保留为未知；不会自动填入“甜度 ≤ 3”这样的及格线。

## 三条供香路线的取舍

| 路线 | 当前选择 | 可取之处 | 主要未知与限制 |
|---|---|---|---|
| A：可即食猕猴桃果肉粉，食用前附着 | **进入筛选** | 容易在相同肉干上独立控制果粉和辣椒；不再让后加材料经历制肉热加工 | 是否认得出猕猴桃、天然甜酸、粉感、附着损耗、残余酶活均未知 |
| B：受控果汁接触后再加工肉干 | 暂缓；需要单独加工试验 | 可探索肉内调味与质地变化 | 酶作用、接触时温、热加工后香气和成品终点一起变化；不能把果汁经验量直接换成肉干工艺 |
| C：规格明确的猕猴桃风味配料后加 | 候选路线；尚未选品 | 若供应商规格合适，可能把供香与果粉固形物更好地分开控制 | 载体糖/油等组成、真实性偏好、价格和食品用途规格待查；没有该商业材料的库内验证，不能沿用果粉克数 |

路线 A 的选择依据是**更容易检验当前风味假设**。路线 C 是研发备选假设，未用鲜果文献冒充商业香料证据。若果粉只产生酸味或粉感，优先比较实际原料及规格，不默认一直加粉或加糖。

## 完整筛选设计

基准为 **100 g 已制好的可即食肉干**，不是生肉。每个样品使用 **50 g 肉干**：沿用 R1 的小样规模，减少相对称量误差并留出多人分样；不要求每人吃完整份。两批独立制备，每批 7 样，共需 700 g 基底；这是计划用量。

| 说明用名称（不作为盲码） | 肉干 g | 猕猴桃粉 g | 辣椒粉 g | 水 g | 理论拌合总量 g |
|---|---:|---:|---:|---:|---:|
| 原样对照 | 50 | 0 | 0 | 0 | 50 |
| 润湿对照 | 50 | 0 | 0 | 0.50 | 50.50 |
| 仅辣椒 | 50 | 0 | 0.05 | 0.50 | 50.55 |
| 低果粉，无辣 | 50 | 1.50 | 0 | 0.50 | 52.00 |
| 低果粉，微量辣椒 | 50 | 1.50 | 0.05 | 0.50 | 52.05 |
| 高果粉，无辣 | 50 | 2.50 | 0 | 0.50 | 53.00 |
| 高果粉，微量辣椒 | 50 | 2.50 | 0.05 | 0.50 | 53.05 |

果粉的 0 / 3 / 5 g 和辣椒的 0 / 0.10 g 均以每 100 g 基底为分母。3、5、0.10 是延续并补全 R1 的**筛选假设**，没有来自数据库的最佳比例或感官强度换算。增加果粉也增加其天然糖、酸和固形物。

各样 0.05 g 辣椒仍对称量有要求。秤显示 0.01 g 分度不等于能准确称 0.05 g；核实设备在该量级的表现，记录实际读数。不能可靠称量时，整样等比例放大并记录，不把计划数复制成实称数。R1 的“果粉–辣椒预混”不能用于本轮**没有果粉的独立辣椒组**，因此这里不把它当作统一操作。

制样前记录肉干与粉料的实际供应商、批号、配料表及可获得的糖/脂肪、辣度等规格。未知保持未知；“碳水化合物”不直接当成糖。只采用明确可即食的材料，原样先检查是否已苦、腻或过甜。后加小试当餐观察，不沿用基底原有保存期限。本文没有另行提供生肉干燥程序。

所有因子样统一润湿、拌合，暂以拌后 10 分钟观察，并记录真正经过的时间、温度、附粉、结团和损耗；10 分钟没有被验证为最优条件。原样对照在相同观察窗口内保留原状。

## 哪些比较能回答哪些问题

生成的 `design.json` 将每条对比保存为带正负权重的样品 ID，估计结果全部为 `null`：

- **果粉差异**：在无辣和有辣条件下，分别将低/高果粉与无果粉比较。可发现果粉与辨识度、甜、酸、涩、粉感等评分的关系；不能分离出纯香气效应。
- **辣椒差异**：分别在 0、3、5 g/100 g 果粉水平比较无辣与有辣，因此包括单独辣椒组。可观察辣感及水果辨识度是否随之改变。
- **交互线索**：比较“有辣时增加果粉的评分差”和“无辣时增加果粉的评分差”。这是评分的差中之差；未测之前不称为协同或掩盖，测得差异也不直接证明分子机制。
- **润湿处理差异**：润湿对照减去原样对照。该试验把少量加水及对应操作作为整体；不测水活度，也不证明货架期。

每位参与者在同一批次内比较，先保留每个批次的结果，再看两批方向是否一致。不能用多人对同一制备样的评分替代独立制备重复。未评分、缺样或缺失批次不会用零值补齐。

## 盲评与观察记录

固定种子 `20261005` 为每批生成随机顺序及三位数盲码。**制样者保管 `design.json`，试吃者只看 `tasting-sheet.md`**，不得向试吃者展示内部配方身份；本人制样本人评分应注明不能完全盲评。先自由描述水果/气味，再进行有提示的目标辨识评分。随机顺序没有实现完整顺序平衡；记录实际顺序、前样残留和分场次情况。

每个样品 × 每名参与者填写一条观察，并保留批次与实际原料 lot。`observation-template.json` 内所有实际称量和评分均为空；需要真正观测后再填。每份共享制备样在不同参与者记录中的称量与 lot 应保持一致。样品总质量为理论拌合质量，若掉粉或转移损耗需另记，不能误当实际回收率。

| 维度 | 本轮记录锚点 |
|---|---|
| 猕猴桃辨识度 `flavor_identity` | 0 不能辨认；10 非常清楚。自由描述先于提示评分 |
| 甜、酸、辣、苦、涩/发干、油腻/挂口、粉感 | 0 没有；10 极强，分别记录 |
| 咀嚼硬度 `chew_hardness` | 0 很软；10 很硬。硬不自动等于不好 |
| 目标符合程度 `overall_fit` | 0 完全不合目标；10 完全符合个人目标，不等于客观合格线 |

0–10 是记录工具，尚未校准为验证过的感官量表。无法评价填 `null`，不能填 0 代表缺失。用户可以另在描述中写“太弱 / 合适 / 太强”和愿意继续吃哪样。苦、涩、酸、辣、粉感与不喜欢不能合并为一个“苦”。

## 运行与累积经验

在仓库根目录运行（`--out` 使用尚不存在的目录）：

```sh
python3 -m tastex validate cases/kiwi-jerky/brief.json
python3 -m tastex run cases/kiwi-jerky/brief.json --out runs/kiwi-r2
python3 -m tastex verify-run runs/kiwi-r2
python3 -m tastex replay runs/kiwi-r2 --out runs/kiwi-r2-replay
```

运行输出包括检索证据、来源缺口、设计、空观察模板、盲评表、报告及校验清单。复现成功只证明流程与产物一致，不表示原料或口味稳定。

有真实观察后，复制模板，填写真实批次、样品、参与者、时间、实际称量和评分，给该事件唯一 ID，再调用：

```sh
python3 -m tastex experience --store local/experience.sqlite record local/observation.json --run runs/kiwi-r2
python3 -m tastex experience --store local/experience.sqlite verify
```

模板不是可直接提交的结果文件。观察保存在独立经验库，不修改来源证据数据库。纠错用新的观察 ID 与 `supersedes` 指向旧记录，保留历史；失败与不喜欢的样品同样值得保留。

经验检索默认要求基质、原料状态、声明的处理协议及食用情景完全相符；放宽范围时明确标为近似案例。`scope.process` 包含路线 ID、计划观察等待时间与操作说明哈希，改变温时或步骤不会仍被标成同一声明工艺。它没有验证真实操作是否遵循计划；真实偏差需要记录，有意改变条件应生成新 revision/run。原料 lot、参与者和批次也需要在解释结果时逐一核对。一次成功只是一条观察，两批方向一致可以提高继续开发的理由，但不会自动升级成通用规则。下一版应记录“哪条具体观察使哪项参数改变”，再生成新 revision/run；不要悄悄覆盖原参数。

## 工作历程与剩余工作

R2 本次已完成：把用户要求和未确认项写入结构化 brief；把 R1 的鲜果/牛肉/辣椒来源身份重新用于状态受限的检索；比较三条路线；补齐完整因子和原样对照；分离计划和实际；加入可重复盲码、两批设计、空观察模板与具体对比；以另一基质测试模块没有硬编码猕猴桃肉干。

[迁移测试 brief](../../benchmarks/transfer-brief.json) 是 **`synthetic_spec_not_recipe_not_tasted`**：使用酸奶、草莓与柠檬测试不同材料键、基准、剂量和评分维度。其数字独立用于软件测试，不是从肉干迁移出的新配方，更不是试吃结果。它只进入隔离测试，不能写成真实经验。

仍需要实物才能完成：采购与规格核对、真实称量、试吃者自由描述和分项评分、用户甜感/辣感接受范围，以及后续是否开发保存型产品的决定。这些缺口不会由运行 harness 自动消失。
